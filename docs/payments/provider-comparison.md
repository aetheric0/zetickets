# Payment provider comparison: Paystack and Safaricom Daraja

**Reviewed:** 2026-11-18. Sources below are official provider documentation, except the Safaricom-maintained SDK reference noted for STK Push API naming. Pricing and features change; public pages do not establish the terms on this project's merchant account.

## Evidence level

- **Documented:** stated in linked official provider documentation as accessed on the review date.
- **Account-dependent:** depends on merchant country, KYB/eligibility, dashboard settings, shortcode or provider activation; owner dashboard/agreement verification is still required.
- **Owner-reported:** project owner reports a verified Paystack account and API access. No account dashboard, credentials or live capability was inspected for this review.
- **Unconfirmed:** public documentation reviewed here does not settle it; obtain written provider/account confirmation before implementation or launch.

## Current public Paystack terms (not a quote)

The Kenya pricing page lists 1.5% for M-PESA, 2.9% for local cards and 3.8% for international cards; it advertises no upfront or monthly fees, T+2 settlement, and USD settlement to a Kenya-based USD-domiciled bank account. Paystack terms say fees can be revised. These are public advertised values only; verify the project's signed merchant agreement, effective date, VAT/taxes, transaction caps/minimums, payout fees, refund costs, chargeback/dispute fees and channel eligibility with the account owner/Paystack before approving economics.

Paystack's refund documentation says refunds can be partial/full and asynchronous; statuses include pending, processing, needs-attention, failed and processed. The support page reviewed states transaction fees are non-refundable and, from 2026-10-15, a one-year refund window for listed channels. Both details must be rechecked against current account terms at implementation time.

## Integration and operational details

**Paystack:** Initialize and verify transactions from the server; use a unique local reference and compare verified status, amount and currency. Test and live keys/environments are separate. Current webhook documentation describes `Paystack-Signature` as a timestamp plus one or more key-ID/signature values using HMAC-SHA512 over `timestamp + "." + raw_body`; it documents constant-time comparison, a 300-second timestamp window and signing-key overlap during rotation. The older `x-paystack-signature` has no timestamp and is described as deprecated. A signature establishes event origin/integrity, not that the amount/order is valid. Provider documentation says webhook events currently cover successful transactions; query verification is necessary for pending/failure/missing-event reconciliation. Webhook deliveries can be retried/resubmitted and resends are explicitly not idempotent. Review the current dashboard requirements and signing mode at implementation time.

**Daraja:** The portal supports sandbox application credentials and separate production host details. Authentication uses the Daraja app's consumer key/secret to obtain an access token. STK Push also uses the live merchant shortcode and Lipa Na M-PESA passkey; status/reversal operations may require an organization API initiator and security credential. STK outcomes are asynchronous. Safaricom documents Transaction Status as a secondary asynchronous query for a delayed/missing callback; query requests need a transaction receipt or original conversation ID and the callback for the query itself is asynchronous. The Daraja portal's Go Live guidance requires a live PayBill/Till shortcode, organization details and M-PESA admin/manager access. Confirm exact callback authentication, endpoint registration, retry behavior, production onboarding and reversal permissions with Safaricom for the actual account; this review does not infer those details.

## Recommendation, not decision

**Recommend evaluating Paystack as the first implementation candidate**, conditional on owner approval and account checks. The combination of an owner-reported verified account, documented Kenya M-PESA support and card channels may deliver a broader launch path with one adapter than direct Daraja alone. Keep the domain provider-neutral and retain Daraja as an independent later adapter if direct M-PESA control, operating economics or redundancy justifies it.

Do not finalize this sequence until the owner verifies the live/test account, M-PESA activation, settlement currencies/destination, fees and refund capabilities, and decides the platform-versus-organizer settlement model. If direct M-PESA control is a business requirement or Paystack account eligibility fails, reassess Daraja first. Provider choice is an approval gate, not an accepted ADR.
